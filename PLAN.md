# ygo-sim plan

A pure-Rust reimplementation of the EDOPro duel engine (edo9300/ygopro-core + ProjectIgnis CardScripts), built for massively parallel simulation: load a gamestate, enumerate legal actions, advance one action at a time, clone cheaply at any decision point.

## Decisions

- **Scope:** current TCG Advanced format only. Pool = cards with the TCG flag in BabelCDB minus Forbidden in the current TCG lflist. One Master Rule (current), no Speed/Rush/Goat, no skills, no anime/unofficial/pre-release cards.
- **Fidelity:** match EDOPro exactly, including misrulings. The core is a near line-by-line port of ocgcore (processor step order, message order, group iteration order). Cleverness goes into data layout only.
- **Card porting:** a Rust API mirroring the Lua `Duel`/`Card`/`Effect`/`Group`/`aux` surface; cards ported by LLM agents in batches, each card gated by differential fuzzing against the oracle.
- **Use cases:** game-tree search AI, RL training, deck statistics.
- **No Lua at runtime.** Lua exists only inside the oracle used for testing.
- **License:** ocgcore and CardScripts are AGPL-3.0; this port is a derivative work. Fine privately; distributing or serving it over a network requires AGPL.

## Architecture

- **Static vs dynamic data.** Card data and effect definitions in a global read-only table; per-duel state holds only dynamic data.
- **Compact, cloneable state.** Cards as `u16` indices, zones as fixed arrays/bitsets, effects as enum + index. No `Rc`/`RefCell`, no `HashMap` on hot paths. Target: `Duel: Clone`, a few KB.
- **Resumable effect operations via choice-log replay.** An operation is a plain Rust fn reading choices from a log. On a choice not yet in the log it bails, the duel reverts to the pre-operation snapshot, and the choice is exposed as the next action set. Hand-written step machines only later, for hot cards.
- **Processor** ported from ocgcore as an explicit step machine (pure data, cloneable).
- **API:** `legal_actions(&Duel)` and `apply(&mut Duel, Action)` running to the next decision. Multi-selects decomposed into sequential single picks so the action space stays bounded.
- **RNG** identical to ocgcore's (believed xoshiro256** with a 4x u64 seed - verify in phase 0).
- **Parallelism:** one duel per thread, rayon; no shared mutable state.
- **Simulation layer:** full-dump gamestate format (including once-per-turn flags, lingering effects, counters), per-player observations, hidden-card sampling, fixed action encoding with masks, pyo3 bindings with batched stepping.

## Verification

- **Oracle:** ocgcore + Lua via FFI. Same seed, decks and responses in both engines; diff the message streams.
- **Per-card scenarios:** place the card under test and random support cards in arbitrary zones at duel creation (as puzzles do), then random-play in both engines.
- **Replay corpus:** real EDOPro `.yrpX` replays (decks + seed + responses) replayed in both engines; doubles as a popularity-weighted regression suite.
- Only states constructible by placement or reachable by replay can be oracle-checked.

## Findings

- Sizes: ocgcore ~30k lines of C++; shared Lua library (`CardScripts/*.lua`) ~14k lines; `CardScripts/official` holds ~13.5k card scripts.
- RNG confirmed: `vendor/ygopro-core/RNG/Xoshiro256.hpp`.
- BabelCDB ships released-but-unmerged sets as `release-*.cdb` beside `cards.cdb`; the pool must read both. `prerelease-*` files are excluded.
- Current TCG banlist is the first list in `LFLists/0TCG.lflist.conf` (2026.09 TCG at vendoring time).
- ocgcore rejects a Lua that cannot unwind C++ frames (`OCG_CreateDuel` returns 5, `INCOMPATIBLE_LUA_API`): Lua must be compiled as C++ (`/TP`) and with `/EHsc`, which `cc` does not add on its own.
- The core never loads `constant.lua`/`utility.lua`; the caller loads them via `OCG_LoadScript` after `OCG_CreateDuel`. `utility.lua` then pulls in the `proc_*` libraries through `Duel.LoadScript`, including `unofficial/proc_unofficial.lua`.
- TCG flag is `ot & 0x2` (cdb `ot` 1 = OCG, 2 = TCG, 3 = both). Advanced pool at vendoring time: 13,726 ids (TCG, minus tokens, alternate arts and Forbidden).
- The core emits no `MSG_START`; the first message batch is draws, then `MSG_NEW_TURN`/`MSG_NEW_PHASE`, then `MSG_SELECT_IDLECMD`.
- Prompts that wait for a response: all `Process<true>` units in `processor_unit.h`, i.e. `MSG_SELECT_*` (10-26), `MSG_SORT_*`, `MSG_ROCK_PAPER_SCISSORS` and `MSG_ANNOUNCE_*`; there are no others. Several are skipped silently when there is nothing to choose (single position, empty or zero-max selections, counters on one card, `count == 0` places), with no message and no response - the port must skip exactly the same ones.
- After `MSG_RETRY` the core does not resend the prompt: the unit's step was already advanced, so it re-validates the next response against the same prompt. The core also keeps running after `MSG_WIN`; the host has to stop.
- Response encodings (native endian, see `playerop.cpp`): idle/battle commands are one i32 `index << 16 | kind`; card selections accept four encodings (i32 type 0/1/2 + u32 count + u32/u16/u8 indices, or 3 + bitmask) and are rejected on duplicate cards; `SELECT_UNSELECT_CARD` takes one card per response (`1, index` into select ++ unselect) and leaves the multi-pick loop to Lua, which is already the decomposed form the action API wants; sort is an i8 permutation or a single -1; counters one i16 per card; place/disfield 3 bytes (player, location, sequence) per zone against a bitmask of blocked zones; announce race/attribute is a bitmask with an exact popcount; announce card is a code checked by an opcode stack machine (ported as `Card::is_declarable`).
- `SELECT_TRIBUTE`'s min counts release units (a double tribute counts 2) while max counts cards. `SELECT_SUM` has two modes: exact (each card counts its low or high u16, and the recursive check rejects a zero remainder before the last card, so zero values are order-dependent) and overflow (flag byte 1, sent when max is 0: the largest total reaches the target and dropping the smallest card misses it). The message shows max raised to min, but the check uses the original max.
- Under random play 65% of decisions are `SELECT_CHAIN` and 97.6% of those offer only "pass"; idle commands are 20%, places 4%, battle commands 4%, card selections 4%. Decisions/s is therefore dominated by trivial chain windows.
- Baseline (Ryzen 7 5700X, 8 cores / 16 threads, release, random legal Advanced decks, 5000-decision cap): 1 thread 9.7 duels/s and 10.8k decisions/s; 16 threads 52 duels/s and 58k decisions/s (5.4x; 8 threads 46 duels/s). Mean 1115 decisions and 59 turns per duel; 61% end by deck-out, 38% by LP. Duel setup (`OCG_CreateDuel`, `constant.lua`/`utility.lua`/`proc_*`, 2 decks) is 13 ms of ~103 ms per duel on 1 thread and rises to 30 ms on 16 threads.
- Random play over 5000 duels: 0 `MSG_RETRY`, 0 unanswerable prompts, 1 duel at the decision cap. Only two scripts raised Lua errors: c84899094 (World Chalice Guardragon, nil target group in its negate condition) and c14291024 (Gradius' Option, selecting with no valid target).
- `CardScripts/pre-errata/` holds the only script of 88264978 (Red-Eyes Darkness Metal Dragon, current text; the cdb's "(Pre-Errata)" version 88264988 lives in `official/`), which EDOPro finds because `Game::PopulateResourcesDirectories` (edopro `gframe/game.cpp`) searches `script/` and then every subfolder; the oracle's reader does the same, first hit wins. Only 4 script names are duplicated across subfolders (`c952000xx`, outside the pool). Every other scriptless Advanced card is a Normal Monster.
- The core does not shuffle decks at startup and `OCG_DuelNewCard` with sequence 0 pushes onto the top, so the last main deck card added is drawn first. Open: whether EDOPro shuffles host-side before adding and in which order `.yrpX` stores decks - settle with the replay runner.
- Determinism: the same seed gives an identical message stream across runs and processes. Responses come from `rand` 0.9 `StdRng`, whose algorithm may change across `rand` versions; pin it (or switch to a fixed algorithm) before recording seeds as fixtures.
- 1a diff (`cargo test -p diff`): 1000 duels of random legal Normal Monster decks (523 cards: the Advanced pool's `TYPE_NORMAL` minus Pendulums, which have scripts), 1,389,967 messages and 507,744 decisions byte-identical through `MSG_WIN`. Responses: phase changes, chain passes, hand shuffles, hand-limit discards. Every duel ends with player 1 decking out (`MSG_WIN` 0, reason 2).
- Without effects the only random draws are `field::shuffle` (Fisher-Yates over `get_next_integer`, which rejects every raw value up to and including `u64::MAX % range`). Draws pop the deck directly, so the deck is never shuffled; only the idle-command hand shuffle (response kind 8) and Adjust's shuffle check consume the RNG.
- Without effects `PhaseEvent` opens no prompt; both players pass silently. `MSG_SELECT_CHAIN` (offering only "pass") comes only from `QuickEffect`: both players after the draw (the `PointEvent` of Turn step 3, so none on turn 1), and the opponent alone when the turn player leaves Main Phase 1, the Battle Phase or Main Phase 2 (hint 23 or 29).
- The Standby Phase gets no `PointEvent` without effects: Turn step 6 skips it while `instant_event.back()` is the Standby start event (the c89642993 special case).
- Choosing End Phase in the battle command still runs Main Phase 2's `IdleCommand`: `MSG_NEW_PHASE` for Main 2 is sent, `skip_m2` answers 7 without a prompt, and the opponent still gets the end-of-phase chain window.
- Hand limit: `PhaseEvent` step 20 sends `MSG_HINT` 501 and `SELECT_CARD` with min = max = hand - 6; the discard is `REASON_RULE | REASON_DISCARD | REASON_ADJUST`. Afterwards `hand_adjusted` suppresses the `QuickEffect` of the following `PointEvent`, so no chain window follows the discard.
- Deck-out: a draw from an empty deck sets `overdraw` and still runs the post-draw `PointEvent` (both chain windows, hint timing still gains `TIMING_DRAW | TIMING_TOHAND`); `MSG_WIN` comes from the Adjust after the Draw Phase's `PhaseEvent`, before the Standby Phase.
- `parse_response_cards` sorts the selected cards by pointer address, an order that differs between runs and platforms; the engine sorts by card id. Harmless while the consumer turns them into a `card_set` (ordered by `cardid`, i.e. creation order), as the hand-limit discard does; 1b must check every other consumer.
- `OCG_DuelProcess` while a prompt waits re-validates whatever is in the response buffer (`SELECT_CHAIN` step 0 pre-sets -1, so a second call passes the chain); the engine's `process()` does nothing while a prompt waits, and `apply` delivers the response.
- Engine state: `Duel` is 1,696 B inline plus heap (cards at 144 B each, zone lists, unit stack of 240 B units, event lists); a `card_set` is a 512-bit bitset (`MAX_CARDS` = 512), which iterates in `cardid` order for free.
- First engine throughput (1a, release, 1 thread, dummy 40-card decks, varied legal actions): ~450k decisions/s, ~720 duels/s; clone + `legal_actions` ~1.2 us. Below the 1M decisions/s target; `apply` currently validates by building `legal_actions`.
- 1b diff (`cargo test -p diff`, 5 s release): 1000 duels, 2,021,242 messages and 1,016,123 decisions byte-identical through `MSG_WIN`. Responses: everything except activations and the Battle Phase, which stays hidden because `MSG_SELECT_BATTLECMD` lists the monsters able to attack (1c). Exercised: 16,386 Normal Summons, 16,361 Sets, 13,453 Flip Summons, 131,467 position changes, 22,910 tributed cards (5,179 `SELECT_TRIBUTE` and 24,924 `SELECT_UNSELECT_CARD` prompts). Every duel still ends with player 1 decking out.
- Without effects a Normal Summon runs SummonRule steps 0-2, 5, 6, 8, 9 and 12-18; a Set runs MonsterSet 0-2, 4, 5 and 8-10. A Normal or Flip Summon opens two chain windows: the summon window (`PointEvent` with skip_trigger and skip_freechain after `EVENT_SUMMON`, both players get `SELECT_CHAIN`) and the usual `PointEvent` after success; Sets and repositions get only the latter. Every summon and Set asks `SELECT_PLACE` even with one free zone (`move_to_field` confirms by default), with `MSG_HINT` 3 carrying the card code first; the position prompt is skipped (one position). The summon count goes up at step 8, before the monster lands, where `break_effect` also clears the hint timings.
- Tributes: with a free Main Monster Zone, `MSG_HINT` 500 and `SELECT_TRIBUTE` (cancelable, since the idle command sets `summon_cancelable`; a cancel returns to the idle command without using the Normal Summon). With all five full, min is not raised (`get_mzone_limit` counts the two Extra Monster Zones, so fcount stays 2); instead `SelectTribute` loops `SELECT_UNSELECT_CARD` one card per answer, each prompt preceded by hint 500 and offering only monsters in usable zones until one is picked (`must_choose_one`). Random play without battle fills the field, so that path dominates. The optional-tribute `SelectYesNo` (hint 90) is unreachable: min is 0 only when max is.
- Tributes leave through Release, whose step 3 starts SendTo at step 1, skipping SendTo's step-0 checks. Several tributes move in `card_operation_sort` order (controller, location, sequence), which is total on the field.
- Pointer order (`parse_response_cards`) is not observable in 1b: `SELECT_TRIBUTE` picks go into a `card_set` (SummonRule step 5) and are sorted again by `card_operation_sort` in Release and SendTo; `SELECT_UNSELECT_CARD` does not use `parse_response_cards` (one card per answer) and returns the operated `card_set`; the hand-limit discard was settled in 1a.
- ocgcore writes a nested `MSG_MOVE` from `move_card` after the outer message MoveToField and SendTo opened first; the engine writes the outer message after `move_card`, so the two would swap. Only same-location moves (between monster zones, within the deck) write one, so it waits for phase 2.
- Engine throughput (1b, release, 1 thread, random legal Normal Monster decks, uniform over legal actions minus entering the Battle Phase, setup excluded): ~570k actions/s and ~560 duels/s at ~1,015 actions per duel (card selections count one action per pick); clone ~1.2-1.6 us; `Duel` 1,952 B inline.
- 1c diff and phase 1 exit (`cargo test --release -p diff -- --ignored`, 20 s): 5000 duels, 13,027,539 messages and 6,331,414 decisions byte-identical through `MSG_WIN`; seeds 5000-25000 are clean too. Responses: everything except activations. Exercised: 71,327 attacks (537 direct), 54,498 battle destructions, 101,595 Normal Summons, 71,508 Flip Summons, 101,797 tributes. Wins: 3,880 by deck-out (always player 1 decking), 1,120 by LP (589 for player 0, 531 for player 1). The default 1000-duel test asserts attacks, direct attacks, battle destructions and both win reasons.
- Replays cannot happen without effects: Adjust step 14 sets `attack_rollback` only when the opponent's monsters change between the declaration (BattleCommand step 8) and step 11, and nothing can change them there. The rollback it also sets after a damage step that killed the target is cleared by the next declaration before step 11 reads it. 0 replay prompts (`SELECT_YESNO` 30) in 25,000 duels, so the zero check leaves them out; phase 2 has to cover replays with scenarios. The direct-attack choice (`SELECT_YESNO` 31) needs `EFFECT_DIRECT_ATTACK` as well: without effects a monster attacks directly only into an empty field, and then without a prompt.
- One attack without effects runs BattleCommand steps 1, 3, 4, 6-11, 19-31, 33, 34 and 39, then step 0 again (step 5 only follows the direct-attack `SELECT_YESNO`). Target selection is `MSG_HINT` 549 and a cancelable 1-of-n `SELECT_CARD`; a cancel restarts at step 0 without using the attack. Chain windows (each a `SELECT_CHAIN` for both players): the declaration (`TIMING_ATTACK`, turn player first), hint 24 entering PointEvent at step 30 (the continuous-effect checks of steps 30 and 32, then a normal PointEvent with both timings `TIMING_BATTLE_PHASE`), and the damage step's hints 40, 41 (`TIMING_DAMAGE_STEP`), 42 (`TIMING_DAMAGE_CAL`), 43 (`TIMING_BATTLED` for both) and 44. A face-down target is flipped by ChangePos (step 21, `enable` set) before hint 41; turning face-up defense, it also gets `STATUS_ATTACK_CANCELED`.
- Damage step order: `MSG_DAMAGE_STEP_START`, the flip, `MSG_BATTLE` (step 26), `MSG_DAMAGE` per player from Damage units (step 27), the Adjust of step 27 (where an LP loss writes `MSG_WIN`, before the loser's monster leaves), Destroy at step 10 marking the cards (step 28), Destroy at step 3 with SendTo from step 1 moving them with reason `REASON_BATTLE | REASON_DESTROY` (step 33), then `MSG_DAMAGE_STEP_END` (step 39). Equal ATK in attack position destroys both unless both are 0 (`DUEL_0_ATK_DESTROYED` is off in MR5).
- The Adjust after step 39 still sees `core.attacker` in the Battle Step: a destroyed attacker gets `STATUS_ATTACK_CANCELED` in the GY (its `POS_FACEUP` there passes `is_capable_attack`'s face-up attack test and its `fieldid_r` changed), and a surviving one whose target died sets `attack_rollback`. Nothing reads either before the next declaration resets them, but phase 2 effects reading `STATUS_ATTACK_CANCELED` will see it.
- The core shares `cards_destroyed_by_battle` as one group between BattleCommand, Destroy and DestroyReplace; the port copies `CardSet`s, which is exact only while Destroy step 10 removes nothing (it removes only for `EFFECT_INDESTRUCTABLE*`/`EFFECT_DESTROY_SUBSTITUTE`). Phase 2 must write removals back. Other effect-only state left out: `announced_cards`/`attacked_cards`/`battled_cards`, `flip_delayed` with `new_fchain_b`/`new_ochain_b`, `damage_calculated`, `effect_damage_step` (DamageStep unit), ForcedBattle, `tpchain`, `must_attack_map`, `battle_destroy_rep`, `desrep_chain`, `destroy_canceled`, Damage's `is_step`/`is_reflected`, PointEvent's `skip_new`.
- Pointer order is not observable in 1c: the only new selection is the attack target, a single card. Battle destruction moves monster zone to GY, a location change, so `move_card` writes no nested `MSG_MOVE` and the latent ordering difference of 1b is still unreached.
- Engine throughput (phase 1 exit, release, 1 thread, random legal Normal Monster decks, uniform over all legal actions, setup excluded, 5000 duels): 550-615k actions/s and 440-500 duels/s at 1,239 actions per duel (46% end by LP under this policy); clone at a decision point 1.14-1.18 us (mean of 1.24M clones); `Duel` 1,992 B inline.
- Profiling on Windows without admin rights: ETW-based profilers (samply, blondie, WPR) need elevation, so 1d used a scratch in-process sampler (a thread suspending the main thread every 200 us, unwinding with `RtlVirtualUnwind` over a copy of its stack, symbolizing with `backtrace`) and a counting global allocator.
- 1d baseline profile (1 thread, random Normal Monster duels): `process_unit` popping the front unit and pushing it back, 240 B per move, on every step ~35%; the allocator ~20% (9.6 allocations per action: `legal_actions` built twice per action, by the caller and by `apply` to validate, a fresh response buffer per answer, event lists losing their capacity to `mem::take`, hand clones, temporary `Vec`s); moving subunits ~8%; `legal_actions` 8%. A clone made 15 allocations. An action takes 28.8 processor steps, 12.2 of them Adjust (0.7 Adjusts per action) and 4.1 RefreshLoc.

- Scripts as built: a Lua coroutine's yield is a nested processor run at the action's call site (`yield_script` runs the units the action emplaced, then restores `reason_effect`/`reason_player` as the core does on resume). The outermost cost, target or operation function snapshots the duel (minus trace and replay state) first. A prompt met with no logged answer interrupts the function (`Script<T> = Result<T, Interrupt>`, propagated with `?`); the prompt is presented on the state the function reached, on top of its Execute unit; once answered, Execute logs the answer, restores the snapshot and reruns the function, which reads its earlier answers from the log, and the messages its previous attempt already wrote are muted by count. The RNG lives in the duel, so reruns redraw identically and a rerun cannot be told from one run. Clones at any prompt, including mid-chain and while a script's prompt waits, resume identically (`engine/tests/duel.rs`).
- Mirror API rules: `Duel.X` is `duel.x(...)`; `c:X`, `e:X` and `g:X` are methods on `CardId`, `EffectId` and `CardSet` taking the duel first; `Effect.CreateEffect`/`GlobalEffect` are on `Duel`; `Effect.Clone` is `clone_effect` so it does not read as `Clone::clone`. Groups are `CardSet` values (`#g` is `len()`). A Lua optional argument becomes a parameter once a ported script passes it. Where most Lua calls omit the trailing optional arguments, the Lua name is the short form with the arity most calls use, filling the omitted arguments as the C++ binding or library does when they are absent, and a `_full` suffix takes them all (`c.is_type(duel, TYPE_SYNCHRO)`, `c.is_type_full(duel, TYPE_TUNER, Some(sc), sumtype, tp)`); a port calls `_full` exactly when its Lua call passes one of them, with the absent default for any it leaves out (`IsType`/`IsRace`/`IsAttribute` without a player take `PLAYER_NONE`, or the reason player when sumtype is SUMMON_TYPE_FUSION). `Duel.SelectMatchingCard`'s optional `cancel` before the exception follows the same rule. Functions whose optional arguments most calls pass keep one form, with the Lua default where a call omits one; nil cards or groups are `None`, a nil player `PLAYER_NONE`. Filters are `Fn(CardId, &Duel) -> bool`, so `Card.IsSpellTrap`-style methods pass directly and Lua's extra filter arguments are closure captures. Functions that yield return `Script<T>`; a cost or target returns `Ok(false)` at chk=1, where Lua returns nil. Closures whose upvalues outlive the call (proc_workaround's `move_eff`) keep them as the effect's label; other upvalues become parameters (Ash Blossom's `s.check`). Lua state kept across calls (proc_workaround's `player_table`) is per-duel script state (`get_script_state`/`set_script_state`). A core function a library replaces keeps a `_core` suffix in the engine (`is_relate_to_effect_core`, `is_able_to_hand_core`); the replacement takes the Lua name in a scripts-crate trait. Internal functions whose names collide with the mirror got a `field_` prefix (`field_draw`, `field_destroy`, `field_is_chain_disablable`). `Duel.GetChainInfo` reads one flag per call (`get_chain_info::<T>`); `Duel.GetLocationCount` returns only the count so far.
